## 一、需求对照

| 需求 | 落地 |
|---|---|
| **畜舍建筑** | 围栏内三栋可扩建棚舍：畜舍 / 禽舍 / 蜂箱。等级 1–3，容量 = 基础 + 每级步进 |

## 二、畜舍建筑

### 2.1 数据表 `data/housing.csv`（8 列）

```
id,name,price,material,material_count,base_capacity,capacity_step,max_level
barn,畜舍,900,wood,15,4,3,3
coop,禽舍,450,wood,8,6,3,3
hive,蜂箱,300,wood,5,3,2,3
```

容量公式（唯一真相在 `HousingDB.capacity_at`）：

```
capacity_at(id, lv) = base_capacity + capacity_step × (lv - 1)

畜舍  Lv1/2/3 =  4 /  7 / 10
禽舍  Lv1/2/3 =  6 /  9 / 12
蜂箱  Lv1/2/3 =  3 /  5 /  7
```

扩建价：`upgrade_price(id, lv) = price × lv`（`lv = 0` = 从空地盖）。
扩建木材：`upgrade_material_count(id, lv) = material_count × max(1, lv)`。

> 开局三栋都是 **Lv1**，总容量 4 + 6 + 3 = 13，装得下开局那 9 只，还留了余量。

### 2.2 分层

```
data/housing.csv
      ↓
HousingDB（autoload）        ← 纯数据：容量 / 价格 / 木材 / 满级
      ↓
Housing（class_name，静态）  ← 纯逻辑：housing_of / can_house / count_in / zone_rect
      ↓
main.gd                      ← 成交：扣钱扣木材、升等级、刷 HUD、刷商店
      ↓
HousingBarn（Interactable）  ← 只发 housing_upgrade_requested，什么都不改
```

`Housing.can_house()` 返回**枚举**不是 bool：

```gdscript
enum Reason { OK, NO_BUILDING, FULL, UNKNOWN }
```

理由和模块 3 的 `plant_reason()` / 模块 5 的 `can_breed()` 一样：只回 bool 的话，
「没盖棚舍」和「住满了」在 UI 上分不开，玩家只能干瞪眼。

### 2.3 分栏几何（`WorldConfig`，唯一真相）

```
y  64 ────────────────── 围栏顶
y  74..112   [畜舍]        [禽舍]        [蜂箱]     ← 建筑向上长
y 120..250   barn 区       coop 区       hive 区    ← 动物活动
y 256 ────────────────── 围栏底

PEN_ZONES = barn(516,120,68,130) · coop(588,120,68,130) · hive(660,120,72,130)
BARN_SLOTS = barn(552,112) · coop(624,112) · hive(700,112)
```

三块 zone 必须：在 `PEN` 内、互不重叠、在建筑下方 —— 测试逐条断言。
`PEN` / `GATE` 一个字节没动（模块 1 的碰撞测试按那组矩形钉死）。

### 2.4 建筑外观（全 `_draw()`，零素材）

| 棚舍 | Lv1 | Lv2 | Lv3 |
|---|---|---|---|
| 畜舍 | 红墙 + 木屋顶 + 双开大门 + 干草 | + 阁楼窗 | + 旗杆 + 圆窗 |
| 禽舍 | 米墙 + 蓝圆顶 + 门洞 + 栖木 | + 栏杆围栏 | + 烟囱 |
| 蜂箱 | 2 层木箱 + 蜂群 | 3 层 + 多两只蜂 | 4 层 + 更多蜂 |

> 等级成长**只往上长，不横向加宽侧翼** —— 侧翼会顶出围栏左边界（见踩坑 6）。

### 2.5 HUD

第一行末尾追加 `棚舍 畜3/4 禽5/6 蜂1/3`。放第一行是因为它最短，
第三行背包内容会长到时钟面板底下（模块 4 踩过）。

## 三、动物美术换装

### 3.1 结论先行：AI 生图在 32×32 上不成立

先跑了 Pollinations 流水线（`_uu/animal_sprites.py` 的前身），9 种里 6 种成功。
降到 32×32 之后：

- 山羊 / 羊驼糊成一团，认不出物种；
- 火鸡**背景根本没去掉**（生成时是深色背景，`bg=(36,35,33)`，洪水填充判不出来）；
- 鸡的轮廓像"躺着的鸟"。

原因是 512×512 的「插画」信息量远超 32×32 能承载的，两段式降采样只是把糊掉的形状保住了，
并不能凭空造出像素画的清晰边界。

**改成确定性像素绘制**：`_uu/animal_sprites.py` 用 PIL 按像素坐标摆形状，
9 种动物各一个函数，统一调色板 + 统一 `INK` 描边。

### 3.2 画法约定

- 画布 32×32，动物**脚踩第 30 行**，描边外扩 1px 后正好填到 31；
- 全部侧视朝左（和玩家默认朝向一致）；
- 统一 17 色调色板（`WHITE / CREAM / SHADOW / BLACK / GRAY / DGRAY / BROWN / DBROWN / TAN / PINK / DPINK / RED / ORANGE / YELLOW / WOOL / WING / INK`）；
- `Sprite.PAD = 1`：内部画布 34×34，所有坐标自动 +1，`finalize()` 描边后裁回 32×32。

### 3.3 接入（`AnimalNode` 一行改动）

```gdscript
if _has_sprite:
    # 真素材是 32×32、底边对齐脚底（pos）；会飞的物种再按 fly 抬起来
    draw_texture(_tex, Vector2(-16, -32 - float(a["fly"])))
else:
    ...  # 原来的表驱动占位图形，一个没删
```

`assets/sprites/animals/<species>_32.png` 存在就自动用，不存在自动退回占位。
**加第 10 种动物 = 放一张 png + CSV 加一行，`AnimalNode` 一行不改。**

### 3.4 重新生成

```bash
python _uu/animal_sprites.py            # 全 9 种 + 拼图 _uu/animal_sheet_preview.png
python _uu/animal_sprites.py cow pig    # 只做指定几种
```

## 四、踩坑记录

1. **AI 生图不是万能的。** 32×32 这个尺度上，可控性 > 生成能力。见 §3.1。

2. **描边会被画布边缘裁掉。** 全局外扩 1px 描边，动物画在 `x=0` / `y=0` 时黑边落到画布外。
   改法：内部画布 34×34 + `PAD=1`，`finalize()` 裁回。副作用是坐标可以照常从 0 写。

3. **`Rect2.has_point()` 判不了「zone 在围栏内」。** 它只看左上角。要用 `Rect2.encloses()`。

4. **容量初始值差点把模块 4 打红。** 禽舍一开始给 5，而开局就有 5 只家禽
   （鸡×3 + 鸭 + 火鸡）→ 玩家买第一只鸡就被拦 → 模块 4 的「买下鸡，进牧场」直接失败 4 条。
   改成 6 才有余量。**教训：容量默认值必须 ≥ 开局占用 + 1，否则第一天就卡死。**

5. **GDScript 类型推断在 `Variant` 上会炸。**
   `var nodes := main._barn_nodes()` / `var g := GameState.gold` —— `main` 和 autoload
   在静态检查里是 `Variant`，`:=` 推不出来。必须写 `var nodes: Array = ...` / `var g: int = ...`。

6. **建筑侧翼会顶出围栏。** 畜舍 Lv2 的侧翼往左伸 18px，Lv3 宽度到 70 时左翼跑到 `x=499`，
   画到栅栏外面去了。改成「只往上长」：Lv2 阁楼窗、Lv3 旗杆。

7. **`_free_spawn_pos()` 不能改签名。** `shot_module4/5` 和 `test_module5` 还在无参调用，
   所以新签名带默认值 `species: StringName = &""`。

8. **蜜蜂会飞。** 真素材分支如果直接 `draw_texture(-16,-32)`，蜜蜂会贴地像块砖。
   要按 `art()["fly"]` 抬起来（占位分支早就这么做了，素材分支漏了）。

9. **新加 `class_name` 必须先 `--import`。** `Housing` / `HousingBarn` 加完不 import，
   运行时报 `Identifier not declared`。老坑，再次验证。

10. **`--check-only --script` 下 autoload 不可用。** 会误报 `Identifier not found: HousingDB`，
    别拿它判断 autoload 有没有配好，直接跑场景。

11. **`Get-Content` / `Select-String` 按 GBK 读 UTF-8 中文源码会乱码**，但 `read_file` 工具正常。
    核对代码请用 `read_file`，不要相信 PowerShell 打印出来的乱码。

## 五、三个设计取舍

1. **棚舍做成「有等级的容器」，而不是「一次性落成的建筑」。**
   牧场开局就有 9 只动物，从空地开始盖房自相矛盾（而且会把模块 4 的 200 项断言全部推翻）。
   真正的玩法价值在**容量约束**：想多养就得花钱扩建，而不是"先盖个房"。

2. **`Housing` 全静态纯函数，`barns` 字典当参数传。**
   测试可以构造任意状态（`{&"barn": 2}` 直接算 Lv2 容量），不依赖 `GameState` 的时序，
   也不会因为别处 `GameState.reset()` 而串味。真值由 `GameState.barns` 提供，main 传进去。

3. **建筑节点不持有 `herd` 引用，`used_slots` 由 main 写入。**
   和 `GardenDecor.sync(herd, ...)` 同一套写法：谁持有数据谁负责喂，
   建筑自己只负责"把数字画出来"。headless 测试也不用造一个假 herd 挂上去。

## 九、明确未做

- **棚舍升级没有建造动画 / 音效**（`EventBus.housing_upgraded` 已广播，接演出随时能挂）。
- **棚舍不提供玩法加成**（不加快产出、不影响生病率），目前只有容量作用。
- **动物精灵只有单帧单朝向**，没有行走 / 吃草动画，也没有左右翻转（`AnimalNode` 不分 facing）。
- **棚舍里的动物不会"回屋"**，雨天留棚只是好感 +3，画面仍在户外。
- **存档系统仍然为零**（棚舍等级在 `GameState.barns`，进程退出即丢）。
