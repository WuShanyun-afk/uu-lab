# 模块 8 · 存档系统

> 一局游戏 = 一坨 JSON。F5 存档、F9 读档、每天 2:00 自动存。
> 存档坏了不能崩、类型过一遍 JSON 不能烂、读档后画面必须跟数据一致。

## 1. 需求对照

| 需求 | 落地 |
|---|---|
| 存一局的完整进度 | 时间 / 天气 / 金币背包 / 农田 / 牧群 / 订单 / 加工坊 / 玩家，8 段 |
| 读档不崩 | 坏档、缺字段、版本太新、槽位越界全部返回 `{ok:false, error}`，绝不让 `null` 漏进玩法层 |
| 自动存档 | 每天 2:00 跨日结算**之后**写 0 号槽（GDD §10.5） |
| 手动存档 | F5 写 1 号槽（快速存档）· F9 优先读 1 号，没有就退 0 号 |
| 原子写入 | `.tmp` → 校验长度 → 旧档挪 `.bak` → 换名 → 删 `.bak` |
| 版本 | 存档带 `version`；老档过 `migrate()`；未来档直接拒 |
| 可测 | 全部序列化逻辑纯数据；测试把 `save_dir` 指到 `user://saves_test`，不碰玩家真存档 |

## 2. 三层架构

```
SaveSystem（只管字典 ⇄ 文件）
  ├─ jsonify：StringName / Color / Vector2 / Vector2i → JSON 原生类型
  ├─ 原子写 + 落盘校验 + 版本迁移 + 坏档容错
  └─ 不认识任何玩法系统
        ▲
        │ 各系统的 to_dict / from_dict（只知道自己有哪些字段）
        │
main.gd（只管「一局 = 哪几坨」+ 读档后的画面同步）
```

为什么不把 `FileAccess` 直接写进 main：存档会变成 main 里三百行 `if`，而 main 已经 1800 行了。

## 3. 存什么 / 不存什么

| 存 | 内容 |
|---|---|
| `clock` | day / season / year / minutes / tick 累加器 |
| `weather` | today / tomorrow / forecast / blizzard / RNG 状态 |
| `state` | 金币 / 真槽位背包 / 工具等级 / 棚舍等级 / 进度标记（花园·繁殖棚·名人） |
| `farm` | 每格：耕地 / 浇水 / 作物 id / 生长天 / 枯萎天数 / 枯死 / 肥料档 / 收获次数 |
| `herd` | 每只：uid / 物种 / 坐标 / 好感 / 年龄 / 今日互动计数 / 产出 / 病 / 妊娠 / 觉醒 / RNG |
| `orders` | 订单数组 / 完成数 / 失败数 / 上次刷新天 / 自增 id |
| `processor` | 等级 / 每槽配方·原料·产物·倒计时·品质 |
| `player` | 坐标 / 4 向与 8 向朝向 / 当前工具 / 当前种子 |

**不存**（都是派生值或瞬态，存了反而制造第二真源）：

- `GameState.inventory` —— 派生索引，`from_dict` 末尾 `_rebuild_index()` 重建；
- `Market` 行情缓存 —— `(天, 品类)` 的纯函数，清缓存按读回来的天数重算；
- `GameClock.phase` —— 派生值，`from_dict` 里 `phase_at(minutes)` 重算；
- `AnimalState.just_awakened` —— 只是「main 还没弹觉醒对话」的临时标记，存了读档会重弹；
- `_pending_animal` / `_breed_picks` / 商店与背包开关 —— UI 瞬态。

## 4. 读档同步顺序

数据先、视觉后。`_sync_garden()` 要读 herd + GameState 的 flag，必须等两者灌完。

```
GameState ← clock ← weather ← farm ← herd ← orders ← processor ← player
        ↓
_grid.season = GameClock.season          （门禁以时钟为准）
Market.clear_cache()                     （行情按新天数重算）
_ground 季节染色 / _farm_layer 重挂 grid + 刷新
_animal_layer.herd = _herd + rebuild()   （成员可能整批换掉，refresh 不够）
_refresh_barns / _refresh_workshop / _refresh_orders
_sync_garden（石碑 + 藤蔓门 + 解锁判定）
_apply_camera_limits（在不在花园里）
ClockPanel.refresh()                     （它只认信号，读档不触发 tick）
_refresh_light / _refresh_hud / _refresh_toolbar
```

**读档不触发任何 `advance_day` / tick**：时间直接落位，不结算、不掷骰。

## 6. 坑（按踩的顺序）

1. **StringName 过 JSON 会变成 String**。每个 `from_dict` 都必须 `StringName()` 回来，否则：`GameState.count_item()` 拿 String 去查 StringName 键的字典 → 永远 0；订单永远交不了、加工永远放不进、作物永远查不到数据。**本模块最大的坑。**
2. **OrderBoard 的 `color` 是 Color 对象**，JSON 不认。`jsonify` 统一转 `"#RRGGBBAA"`，`from_dict` 里转回 `Color(...)`。
3. **RNG 状态是 64 位整数**，JSON 数字走 double 会掉精度 → 天气/农田/动物的 RNG 一律存**字符串**，读回来 `int()`。
4. **`phase` 是派生值**（模块 2 就踩过「缓存过期」），读档后必须 `phase_at(minutes)` 重算。
5. **`GameState._ensure_slots()` 不能用在 `from_dict` 里**：它在缩容时会调 `add_item()`，而此刻派生索引还是空的，尾巴上的物品会被算丢。改为手动 append / pop_back。
6. **派生索引必须重建**：`slots` 灌完不调 `_rebuild_index()`，HUD 和所有 `count_item` 全瞎。
7. **`just_awakened` 不能存**：存了读档会重新弹一遍觉醒演出，像见了鬼。
8. **`Herd._next_id` 必须大于所有已存在编号**：否则读档后新买的动物和老动物撞 uid（uid 是主键，会串到渲染和订单上）。`from_dict` 里扫一遍 uid 兜底。
9. **未知物种要跳过**：旧档里存着新版本删掉的动物（改 `animals.csv`），不跳过就是一读档崩。
10. **自动存档必须放在 `advance_day()` 之后**：放前面会存成「旧的一天 + 已推进的时钟」，读档等于白过一天。
11. **Windows 上 rename 覆盖已存在文件会失败** → 原子写必须 `.tmp` → 旧档挪 `.bak` → 换名 → 删 `.bak`，中途失败还能把旧档挪回来。
12. **`JSON.parse_string()` 对坏档会往控制台打 ERROR**，而坏档是本系统**预期内**的结果，不该看起来像引擎出事 → 改 `JSON.new().parse()`，拿行号和原因。
13. **`ClockHUD` 只订阅信号**，读档不触发 tick / day → 右上角会拿旧时间糊 0.6 秒。`_apply_save` 里手动 `ClockPanel.refresh()`。
14. **测试间状态泄漏**：时钟 `season` 被上一个用例推到冬天，`_test_main` 里 `main._ready` 按冬天设季节门禁，春天作物种不下去。快照式测试套件记得把全局时钟归位。
15. 顺手修了个**历史 bug**：`main._on_day` 里 `EventBus.animal_events.emit(aevents)` 被并进了上一行的注释，成了死代码（TAB 吃掉了换行）。现在它真的会广播了。
